= Migration from AdminFaces
:toc:

This project is inspired by https://adminfaces.github.io/site/[AdminFaces].
This document describes how to migrate a Spring Boot based AdminFaces
application to `pf-adm`.

The goal of the migration is not a byte-for-byte replacement of AdminFaces.
`pf-adm` keeps a compatible direction where it is practical, but it is based on
a different technical stack:

* Bootstrap 5 instead of Bootstrap 3
* AdminLTE 4 instead of AdminLTE 2
* a `pf-adm` configuration model instead of the original AdminFaces property set
* modern bean naming such as `*View` and config nouns instead of legacy `*MB`

For detailed compatibility status, see:

* link:doc/template_compatibility_matrix.adoc[Compatibility Matrix]
* link:doc/feature_matrix.adoc[Feature Matrix]
* link:doc/uicomponents.adoc[UI Components]

== Migration Strategy

The migration is usually easiest in this order:

1. Replace dependencies.
2. Move configuration from AdminFaces properties to `pf-adm.*`.
3. Switch the template usage to `pf-adm` templates.
4. Update menu markup to the AdminLTE 4 / Bootstrap 5 structure.
5. Review pages for features that are only partially compatible.

== Dependencies

Remove AdminFaces-based dependencies and replace them with the `pf-adm`
starter.

[cols="a,a"]
|===

|
[source,xml]
----
<dependency>
  <groupId>com.github.adminfaces</groupId>
  <artifactId>admin-template</artifactId>

<dependency>
  <groupId>com.github.adminfaces</groupId>
  <artifactId>admin-theme</artifactId>
</dependency>
<dependency>
  <groupId>org.primefaces</groupId>

[source,xml]
----
<dependency>
  <groupId>de.muehlencord.pf-adm</groupId>
  <artifactId>pf-adm-spring-boot-starter</artifactId>
</dependency>
----
|===

with the JoinFaces PrimeFaces starter plus `pf-adm`. A dedicated JoinFaces
`pf-adm` starter does not exist yet.

|

  <groupId>de.muehlencord.pf-adm</groupId>

Configure PrimeFaces through JoinFaces and configure the template through
`pf-adm` properties:

[source,yaml]
----
joinfaces:
  primefaces:
    theme: admin

pf-adm:
  index-page: /web/index.xhtml
  template-path: /WEB-INF/template/template.xhtml
  skin: skin-blue
----

== Configuration

`pf-adm-template` uses Spring Boot configuration properties with the prefix
`pf-adm`.

Typical examples:

[source,yaml]
----
pf-adm:
  index-page: index.xhtml
  template-path: /admin.xhtml
  render-messages: true
  render-bread-crumb: true
  enable-slide-menu: true
  skin: skin-blue
  render-logo: true
  render-brand-text: false
  render-full-screen-toggle: false
  render-slide-menu-toggle: true
  support-bootstrap-icons: false
  support-font-awesome: false
  error:
    page403: /403.xhtml
    page404: /404.xhtml
    page500: /500.xhtml
----

Important differences:

* not all AdminFaces properties exist in `pf-adm`
* some properties exist with different behavior
* some features, such as the AdminFaces control sidebar, are intentionally not implemented at this stage

Before migrating configuration files, compare your current settings with
link:doc/configuration_compatibility_matrix.adoc[Compatibility Matrix]

== Template Changes

Pages that currently use AdminFaces templates usually reference `admin.xhtml`
already. `pf-adm-template` provides the same template entry point, but the
implementation is not a full copy of AdminFaces.

What is currently compatible:

* the main `admin.xhtml` template entry point
* the core `ui:define` and `ui:insert` regions used for header, menu, body, and footer composition
* the standard sidebar layout direction

What still differs:

* control sidebar behavior is not implemented
* the top-menu-only layout variant is not implemented
* legacy AdminFaces backing bean names are not part of the preferred API

Recommended migration approach:

* keep using `admin.xhtml` where possible
* verify page-level `ui:define` usage against
  link:doc/template_compatibility_matrix.adoc[Compatibility Matrix]
* remove reliance on AdminFaces-only regions that currently exist only as placeholders

=== Upper-Right Notifications

The showcase fragment
`pf-adm-showcase/src/main/resources/META-INF/resources/includes/notifications.xhtml`
renders the upper-right header dropdowns through the
`top-menu-notifications` template region.

This differs from AdminFaces in a few important ways:

* `top-menu-notifications` is a `pf-adm-template` extension. It is not an AdminFaces-compatible template region.
* the fragment is only header navigation UI. It is separate from the main page message area rendered by `p:messages` when `pf-adm.render-messages=true`.
* `pf-adm` uses AdminLTE 4 / Bootstrap 5 navbar dropdown markup such as `nav-item dropdown`, `nav-link`, `data-bs-toggle="dropdown"`, `dropdown-menu`, `dropdown-item`, and `dropdown-menu-end`
* AdminFaces examples are based on AdminLTE 2 / Bootstrap 3 patterns such as `messages-menu` / `notifications-menu`, `dropdown-toggle`, `data-toggle="dropdown"`, `label`, and nested `.menu > li > a` structures
* the showcase uses Bootstrap Icons (`bi ...`) and Bootstrap 5 badge utility classes such as `badge text-bg-warning`; AdminFaces examples typically use Font Awesome and Bootstrap 3 label classes

In practice, this means that AdminFaces notification dropdown fragments cannot be copied unchanged into `pf-adm`.
When migrating the upper-right corner, keep the conceptual content, but rewrite the markup to the current navbar dropdown structure and place it in `top-menu-notifications`.

=== Breadcrumbs

The breadcrumb works very differently in the two projects, so it almost always
needs attention during migration.

AdminFaces builds the breadcrumb *automatically* from a session-scoped history
model. Each visited page is appended to the trail at render time through the
`adm:breadcrumb` composite, driven by the page `#{title}`. The model deduplicates
entries, caps the trail at `breadCrumbMaxSize` (`admin.breadcrumbSize`, default
`5`), and exposes a `Home` action via `breadCrumbMB.clearAndHome`. Pages do not
write any breadcrumb markup themselves.

`pf-adm` intentionally uses a simpler, *explicit and hierarchical* breadcrumb.
This is a deliberate design choice, not a missing feature:

* breadcrumb rendering is toggled with `pf-adm.render-bread-crumb`
* a `Home` root link to `pf-adm.index-page` is always rendered (its label comes from the `label_home` message bundle key)
* each page supplies its own trail by defining the `breadcrumb` template region; a page that does not define it shows only the `Home` root
* there is no `breadCrumbMB`, no `clearAndHome`, no `breadCrumbMaxSize`, and no automatic visited-history model

Migration steps:

* remove `adm:breadcrumb` tags and any reliance on `breadCrumbMB` or `breadCrumbMaxSize`
* for each page that should show a trail, add a `breadcrumb` define listing the trailing items and mark the last one active

[cols="a,a"]
|===
^| AdminFaces ^| `pf-adm`

|
[source,xhtml]
----
<!-- automatic: the page only provides a title,
     the trail is built from navigation history -->
<ui:param name="title" value="Buttons"/>
<adm:breadcrumb title="#{title}"/>
----

|
[source,xhtml]
----
<ui:define name="title">Buttons</ui:define>

<!-- Home is rendered by the template;
     the page appends its own trail items -->
<ui:define name="breadcrumb">
  <li class="breadcrumb-item active" aria-current="page">Buttons</li>
</ui:define>
----
|===

== Bean Naming

`pf-adm` prefers modern names such as `layoutView`, `skinView`, and
`pfAdmConfig` instead of legacy `layoutMB`, `skinMB`, and similar `MB` names.

If your application still uses AdminFaces-era EL names, update the templates and
pages during migration instead of carrying the old names forward unnecessarily.

Examples:

[cols="a,a"]
|===
^| Legacy style ^| Preferred `pf-adm` style

|`#{layoutMB.template}`
|`#{layoutView.template}`

|`#{skinMB.skin}`
|`#{skinView.skin}`

|`#{adminConfig.indexPage}`
|`#{pfAdmConfig.indexPage}`
|===

== Menu Changes

This is one of the most visible migration steps. AdminFaces menu markup follows
the AdminLTE 2 / Bootstrap 3 structure, while `pf-adm` uses an AdminLTE 4 /
Bootstrap 5 compatible structure.

[cols="a,a"]
|===
^| AdminFaces ^| `pf-adm`

|
[source,xhtml]
----
<h:form id="menuform">
  <ul class="sidebar-menu tree" data-widget="tree">
    <li>
      <p:link outcome="/web/index.xhtml">
        <i class="fa fa-home"/>
        <span>Home</span>
      </p:link>
    </li>
    ...
  </ul>
</h:form>
----

|
[source,xhtml]
----
<h:form id="menuform">
  <li class="nav-item">
    <p:link styleClass="nav-link" outcome="/web/index.xhtml">
      <i class="nav-icon pi pi-home"/>
      <p>Home</p>
    </p:link>
  </li>
  ...
</h:form>
----
|===

Migration notes for menus:

* use `nav-item` and `nav-link`
* use `nav-icon` on icons
* expect to rewrite nested menu markup instead of relying on old tree classes
* do not assume AdminFaces JavaScript menu behavior is present unchanged

== Page Changes

Most page migrations fall into these categories:

* replace legacy bean names with the current `pf-adm` names
* adjust menu and header fragments to the current template structure
* remove dependency on AdminFaces-only features that are not implemented in `pf-adm`
* re-check component styling for pages that rely heavily on AdminFaces-specific presentation

Areas that usually need explicit review:

* breadcrumb-heavy flows (see <<_breadcrumbs,Breadcrumbs>> &#8212; the automatic AdminFaces trail must be re-expressed explicitly per page)
* pages that relied on the control sidebar
* pages that used AdminFaces ripple/material interactions
* pages that rely on specialized AdminFaces component styling
* pages that use Bootstrap 3 responsive visibility classes (see <<_responsive_visibility,Responsive Visibility>>)
* form pages built with `p:panelGrid` that need explicit column widths (see <<_panelgrid_column_widths,PanelGrid Column Widths>>)
* pages with `p:dialog` that need an explicit width and `appendTo="@(body)"` to centre correctly (see <<_dialog_sizing_and_centering,Dialog Sizing and Centering>>)
* pages that `update` a `p:dialog` by id, which duplicates the overlay panels of the inputs inside it (see <<_overlay_panels_inside_dialogs,Overlay Panels Inside Dialogs>>)

For the current high-level feature status, see
link:doc/feature_matrix.adoc[Feature Matrix] and link:doc/uicomponents.adoc[UI Components].

=== Responsive Visibility

AdminFaces (Bootstrap 3) toggled per-breakpoint visibility with the
`visible-xs`/`visible-sm`/`visible-md`/`visible-lg` and
`hidden-xs`/`hidden-sm`/`hidden-md`/`hidden-lg` classes.
Bootstrap 5 removed these; `pf-adm` no longer ships the compatibility shims for them either.

Use the Bootstrap 5 responsive display utilities instead.
The pattern is
`d-{breakpoint}-none` combined with `d-{breakpoint}-block` (or another display value), where the Bootstrap 5 breakpoints are `sm` (&#8805;576px), `md`
(&#8805;768px), `lg` (&#8805;992px), and `xl` (&#8805;1200px).
See the
https://getbootstrap.com/docs/5.3/utilities/display/[Bootstrap 5 display
utilities] for the full set.

Common replacements:

[cols="a,a"]
|===
^| Bootstrap 3 (AdminFaces) ^| Bootstrap 5 (`pf-adm`)

|`visible-sm visible-xs` (show only on small screens)
|`d-lg-none`

|`hidden-xs` (hide on extra-small screens)
|`d-none d-sm-block`

|`hidden-lg` (hide on large screens and up)
|`d-lg-none` &#8212; wrap smaller-screen content, or use `d-none d-lg-block` to invert
|===

=== PanelGrid Column Widths

`pf-adm` tightens `p:panelGrid` cell padding (`0.25rem 0.75rem`) and stretches
`inputText`, `inputTextarea`, `selectOneMenu`, and `calendar` fields to fill their cell, so form-style panel grids read compactly out of the box.

To control the relative width of columns, apply the `pfadm-col-*` utility classes per column through the standard PrimeFaces `columnClasses` attribute (the classes are assigned cyclically, one per column):

[source,xml]
----
<p:panelGrid id="panelgrid" columns="3"
             columnClasses="pfadm-col-25,pfadm-col-50,pfadm-col-25">
----

Available widths: `pfadm-col-10`, `pfadm-col-20`, `pfadm-col-25`,
`pfadm-col-30`, `pfadm-col-50`, `pfadm-col-70`, and `pfadm-col-75`
(10/20/25/30/50/70/75%).
The example above makes the middle column twice as wide as the outer two.
The classes are scoped to
`.ui-panelgrid-cell`, so they set the column width without affecting other elements.
Aim for a set of widths that sums to 100% when you want exact control; any remainder is distributed by the browser based on content.

=== DataTable Cell Padding

The PrimeFaces theme-base pads `p:dataTable` / `p:treeTable` cells with
`1rem 1rem`, which is too loose for admin tables. `pf-adm` narrows this to
`0.5rem 0.75rem` for body, header, and footer cells (the `sm` and `lg` scale variants derive from it proportionally).

The value is controlled by a single design token in
`pfadm/_variables.scss`:

[source,scss]
----
$pfadm-datatable-cell-padding: 0.5rem 0.75rem !default;
----

Retune it in one place if you want denser or roomier tables; it feeds the theme-base `$datatableBodyCellPadding`, `$datatableHeaderCellPadding`, and
`$datatableFooterCellPadding` variables.
For a one-off extra-compact table, the existing `extra-compact` style class on `p:dataTable` still applies.

=== Dialog Sizing and Centering

Give every `p:dialog` an explicit `width` and append it to the body:

[source,xhtml]
----
<p:dialog id="editDialog" appendTo="@(body)" width="900" modal="true">
----

Two reasons, both specific to the AdminLTE 4 fixed-sidebar layout:

* `appendTo="@(body)"` makes the dialog's coordinate origin the viewport.
A dialog left inside the content area is positioned relative to `.app-main`
(which is `position: relative` and offset right by the sidebar), so it renders off-centre to the right.
* An explicit `width` keeps the dialog centred.
Width-less dialogs are auto-sized to their content, and `pf-adm` stretches `inputText`,
`inputTextarea`, `selectOneMenu`, and `calendar` to full width inside a
`p:panelGrid` (see <<_panelgrid_column_widths,PanelGrid Column Widths>>) - in an auto-width dialog those `100%` fields size unpredictably and can push the box past the right edge.

As a backstop, `pf-adm` caps every dialog at `max-width: 95vw`, so a dialog can never overflow the viewport horizontally even if it has no explicit width.
This is a safety net, not a substitute for setting a sensible `width`.

=== Overlay Panels Inside Dialogs

An overlay panel - the dropdown of a `selectOneMenu`, `autoComplete`, or `selectCheckboxMenu` - is rendered inside the component's own markup, and PrimeFaces normally aligns it with coordinates relative to that component.
Inside a dialog it rewrites both at runtime.
`PrimeFaces.utils.resolveAppendTo` sees that the component sits in a `.ui-dialog`, forces
`appendTo="@(body)"` on it, and - because `.ui-dialog` is `position: fixed` - sets
`position: fixed` on the panel.
The panel is therefore moved out of the dialog and into `<body>`.

That is fine until something re-renders the region the component lives in.
The moved panel is no longer part of that region, so it survives, while the re-rendered markup brings a fresh panel carrying the *same* DOM id.
From that point the component is unrecoverable:

* PrimeFaces resolves its panel as `$('#form\:field_panel')`.
The escaped colon stops jQuery from using `getElementById`, so it falls back to
`querySelectorAll` and the widget's `panel` holds *both* elements.
* `alignPanel()` tests `this.panel.parent().is(this.jq)`.
One of the two parents *is* the component, so the test passes and PrimeFaces applies the relative branch - `left: 0; top: <component height>` - to both panels.
On a `position: fixed` panel the browser reads those as viewport coordinates, and the dropdown opens in the top left corner of the screen, behind the fixed `.app-header`.
* `PrimeFaces.utils.appendDynamicOverlay` bails out early because one panel already sits in
`<body>`, so PrimeFaces never cleans up or re-moves anything.

Setting `appendTo="@(body)"` on the field does not help - PrimeFaces has already set it.
Neither does `positionType="absolute"` on the dialog: it suppresses the `position: fixed`, but the `appendTo` is forced regardless, so the duplicate still appears.
The duplicate itself has to go.

`pf-adm` ships a cleanup for this, but does not apply it on its own - the situation is rare enough that silently deleting DOM nodes on every request would be the worse trade.
Call it from the `onstart` of the request that re-renders the region:

[source,xhtml]
----
<p:commandButton action="#{view.edit}"
                 onstart="PfAdm.dropOrphanOverlayPanels('editDialogForm')"
                 update=":editDialogForm"
                 oncomplete="PF('editDialogVar').show()"/>
----

`onstart` runs before the request, so the response arrives to a document holding exactly one element per panel id.
The widget then resolves its panel unambiguously, PrimeFaces moves it to `<body>` as intended,
`parent().is(jq)` is false, and the panel is aligned with document coordinates.

`PfAdm.dropOrphanOverlayPanels` is defined in `admintemplate.js`, which `admin-base.xhtml`
already loads - nothing has to be imported.
It takes the client ids of the re-rendered region, as a space- or comma-separated string or an array, and returns the number of panels it removed.
Pass the same ids the request updates: only panels whose owning component lies inside that region are touched, because removing others would detach the panels of widgets that are not being re-rendered.

One caveat: the panels are gone once the request is sent.
If it fails or is aborted, the old markup stays without its panels until the next successful update.

Note the leading colon in `update=":editDialogForm"`.
`p:dialog` is not a `NamingContainer`, so the form's client id does not contain the dialog id, and a button inside a `p:dataTable` (which *is* one) cannot reach the form relatively.

A migrated application usually did not show this under AdminFaces, and the reason is worth knowing: the duplicate was there all along, it was simply invisible.
AdminFaces overrode PrimeFaces' dialog CSS in its `admin-theme`:

[source,css]
----
body .ui-dialog.ui-widget-content, body .ui-dialog {
  position: absolute;   /* PrimeFaces default: fixed  */
  overflow: visible;    /* PrimeFaces default: hidden */
  ...
}
----

With the dialog at `position: absolute`, the `"fixed" === $(dialog).css("position")` test in
`resolveAppendTo` fails and the panel is never set to `position: fixed`.
The forced `appendTo="@(body)"` still ran - it sits after the comma operator, independent of that test - so the hoisting, and with it the duplicate id, happened under AdminFaces too.
It simply did no harm.
The copy still inside the component was `position: absolute` against the component's own
`position: relative`, so it rendered correctly under the field, while the copy in `<body>`
resolved against the document and landed at the top left of the page - behind the AdminLTE 2 header and below PrimeFaces' z-index base.
Nobody ever saw it.

`pf-adm` does not override `.ui-dialog`, so PrimeFaces' own `position: fixed` applies, and the stray copy moves from "hidden behind the header" to "in the corner of the viewport".
Neither override is carried over, on purpose.
`overflow: visible` existed because PrimeFaces 6 to 8 kept panels inside the dialog, where they were clipped; since PrimeFaces 11 every overlay is hoisted out - `selectOneMenu`,
`autoComplete`, `selectCheckboxMenu`, `datePicker`, and every `DynamicOverlayWidget` - so there is nothing left to clip, and giving up `overflow: hidden` would only let content overdraw the rounded corners and loosen `maximizable` and `resizable`.
`position: absolute` would not fix the duplicate either, only hide it again, at the price of dialogs that scroll away with the content below the `md` breakpoint, where `.app-main` is not the scroll container.

Two smaller hazards in the same area.
Panel width is not bound to the input: PrimeFaces freezes the panel at its natural width and list items do not wrap, so one long item label can make it wider than the viewport, at which point jQuery UI's `flipfit` collision handling clamps it to the screen edge.
`pf-adm` caps every overlay panel at `max-width: 95vw` as a backstop; a tighter per-field
`panelStyle="max-width:…"` reads better in a narrow dialog.
And give tall dialogs `fitViewport="true"` - PrimeFaces centers a dialog on its measured height, so a form taller than the viewport gets a negative `top` and its first rows end up behind the fixed `.app-header`.

== Validation Checklist

After migrating, verify at least the following:

* application starts with the new dependencies only
* the main `admin.xhtml` layout renders correctly
* sidebar branding, menu, and header actions render in the expected positions
* configured `pf-adm.skin` is used for new sessions
* per-session skin changes do not affect other users
* custom error pages render correctly
* migrated menus render and navigate correctly

== Summary

The easiest way to migrate from AdminFaces to `pf-adm` is to treat it as a
template and styling migration, not as a drop-in binary replacement.

Keep the template contract where it helps, move configuration to `pf-adm.*`,
rename legacy EL usage to the current bean names, and rewrite menu/layout markup
where the underlying AdminLTE structure changed.
